# 迭代方案：这一帧付的是哪一卷的价钱

自由 brainstorm 的落点。基线：`iteration/tape-geometry`（efc338e）之上。

## 0. 先量，再命名

这一条迭代线（`guard` → 线性解释器 → 线性观众端）的写法一直是：先用探针复现一个具体的坏，再给它一个名字，再把它钉成测试。这份文档沿用同一个顺序。

探针（jsdom + vitest，`min-of-7`，每次 40 帧）在 efc338e 上量到的**每一帧**的价钱：

| 带的形状 | 1k 条 | 4k | 16k | 64k |
| --- | --- | --- | --- | --- |
| 道具（一屏只看得见 12×18 格） | 0.086ms | 0.383 | 2.746 | **15.317** |
| 旁白 + 镜头交替 | 0.050ms | 0.196 | 1.211 | **6.449** |
| `here` 占位符（无旁白） | 0.088ms | 0.411 | 2.683 | — |
| `compile()` 整卷一次 | 16.4ms(4k) | — | 29.3 | 94.3 |

三件事从这张表里读出来：

1. **解释器的读侧没有跟着写侧一起变成线性的。** `58a96f6` 把 `compile()` 改成一遍过（64k 条 94ms，线性），`efc338e` 把观众那一头改成线性的；中间那一层 —— `Stage.render()` 每帧走的 `cameraAt` / `visibleProps` / `owedAt` / `cutAt` / `cardAt` —— 没有人量过。它的形状是**每帧重读整卷**：64k 道具时一帧 15.3ms，而预算是 16.7ms。一秒钟六十帧里，光是"这一帧该画什么"就吃满了整帧。
2. **它还在每帧分配。** `p.revisions.filter(...)` 每格道具每一帧建一个新数组；`cues.filter(...)` 每帧建一张新的镜头表；`gates.filter(...)` 每帧建一张新的卡表。GC 的抖动正是那条规模测试自己说的"只会让一次测量变慢，不会让它变快"。
3. **门封了每个字段，没封整卷有多少条** —— 这条 `guard.ts` 自己在注释里写着。所以上面那张表不是理论问题：一条 `#s=` 链接合法地递进来六万格道具，板子不崩，但它每帧付 15ms。写侧不冻了，读侧慢到只剩 4fps。

还量到一个不属于性能的坏：

4. **`compile.test.ts:217` 那一格自己是会翻的。** `linear()` 先断基线 `expect(a).toBeGreaterThan(10)`，再断比值。在共享 CI 上 `每题一答` 那个形状 20k 条常常跑进 10ms 以下 —— 断言当场失败，而这跟解释器有没有变回二次的毫无关系。守门的那一条自己漏了：它测的是"计时器分辨率"，不是"带的形状"。

再加一条从词表里读出来的（不是量出来的）：

5. **`link` 是唯一一个只落在导演脑子里、不落在板上的动词。** 关系被存进 `Prop.links`，被 `stage_state` 念给导演听，`README` 说它是"让后面一拍能引用前面一个想法"的东西 —— 而解释器从来没有把它画出来过。`dim-rest` 上一轮就是这个形状（在词表里、在枚举里、唯独不在板上），那次是靠"把 CSS 类名和 DOM 类名对上"这一刀抓住的。

## 1. 这次做哪几件

| # | 名字 | 坏 | 修法 | 钉住它的测试 |
| --- | --- | --- | --- | --- |
| 1 | 守门的自己不许是抖的 | `linear()` 的基线下限在快机器上把守门的那条断言变成 flake | 探针自己加长到跨过下限，而不是对着固定条数断言"必须慢" | `compile.test.ts` 里同一批规模测试，跑十次不许有一次假失败 |
| 2 | 每一帧不许重读整卷 | 读侧每帧 `filter` + 线性扫整条 cue 表 / 每格道具 | `Compiled` 里按 kind 分好的**时间线** + 每条线上的 `open` 前缀水位；每帧二分两次取窗口，只碰窗口里那几条 | 新旧读法在随机带上逐帧对账（形状完全等价），加一条规模测试断"一帧的价钱不许跟整卷条数成正比" |
| 3 | 道具的账不许每格分配一次 | 每格道具每帧 `revisions.filter(...)` | 每个 `Prop` 的 revisions 本来就在时间上单调 —— 二分取"此刻站着的那版"；`propsByFirstT` 前缀一次二分跳过还没上台的 | 同 2 的对账测试 + 现有 `stage.test.ts` 不许改一行 |
| 4 | 强调和运动不许按道具数付钱 | `highlights.filter(...)` / `motions.filter(...)` 每格道具各跑一遍 | 每帧从窗口建两张 `Map<id, …>`，格子里查表 | 同 3 |
| 5 | 导演的舞台摘要必须有界 | `agentSnapshot()` 把**每一拍**的标题和**每一格**道具都拼进 `<stage>`；长课把它自己顶出窗口 | 折回指针那一招搬过来：拍子只留最近 N 条 + 一句"前面还有 M 拍"，道具只列眼前这块板和框内的，其余折成一行计数 | `snapshot.test.ts`：两万拍不许产出两万行 |

`link` 画到板上（第 5 条 brainstorm 里那条）留作下一件 —— 它要新加一条"由解释器画的连线"的路径，属于加词汇，不属于把已有的词汇兑现；而这一卷的形状（1~5）先把它自己的账付清。

## 2. 时间线这一刀的形状（第 2 条的核心）

`compile()` 出来的 `cues` 天然按 `t` 单调递增（时钟只往前走）。于是任何一条子线都可以带一个前缀水位：

```
open[i] = max(cues[0..i].end)      // 非递减，可以二分
```

给定 `t`：

- `firstOpen = 最小的 i 使 open[i] > t` —— 这就是**原循环里第一个还没走完的 cue**：`open[firstOpen-1] <= t` 意味着它前面每条都 `end <= t`，都是"已经走完"的，所以那一格的 `to` 就是镜头该停下的地方。**这正是 `cameraAt` 那个 for 循环的语义**，一条不多一条不少。
- `lastStarted = 最小的 i 使 cues[i].t > t` —— 窗口就是 `[firstOpen, lastStarted)`：已经开始、还没走完的那几条。重叠的覆盖层只可能落在窗口里，数量是"此刻同时有几个 pulse"这种量级，不是整卷的长度。

这样 `cameraAt` 从"每帧扫整条 cue 表 + 每帧 filter 分配一张镜头表"变成两次二分；`owedAt` 里找"脚下这一拍"、`cutAt`、`followed`、`narr`/`veil` 全都走同一扇门。

写侧保留 `cues` 原样：`blindCamera` 拿 `c.op === askedBy` 认它自己刚发的那一刀，`identity.test.ts` 断的就是这个引用不许变。分线只在 `compile()` 收尾时多走一遍，不在门口。

## 3. 明确不做的事

- **不给整卷条数封顶。** 门封字段，不封卷 —— 一条二十万条的带是合法输入，不是拒绝的理由（`58a96f6` 的原话）。这一卷做的是让读它的人付线性的价钱，不是让递它的人递不进来。
- **不改任何时序语义。** `cueMs`、`SETTLE_MS`、`MIN_CLOSEUP_W`、`BOARD_SPACING`、`LOOKAHEAD_OPS` 一个数都不动。这一卷全部是"同样的答案，更少的功课"。
- **不动 React 那一层。** `efc338e` 已经把节拍条和日志面板钉住了；这里如果又冒出每帧的活儿，那就是新证据，不顺手改。
- **不引入新依赖。** 二分和 Map 是 stdlib。

## 4. 怎么算做完

1. `npm run test` 全绿，且第 1 条的 flake 在同机连跑十次不许复现。
2. 新加的对账测试证明读法**等价**，不是"更接近"：随机带、多个 t、逐帧比对旧实现的输出。
3. 规模测试断的是形状（比值），不是毫秒 —— 共享 CI 的噪声比省下来的那些毫秒大。
4. `npm run build` / `npm run lint` 干净。
5. README 的时间规则那一节补一条：**每一帧只许读这一帧碰得着的那几条**。

## 5. 做完之后（迭代记录，不是计划）

四条实际结果、两个由对账测试而不是由眼睛抓到的坏。

**实际数字**（本机 jsdom，同一套自校准探针，4k → 40k 条）：旧读法一帧 326.5µs → 2467.1µs（比值 7.6，带长翻十倍它肉眼可见地跟着涨 —— 那件坏确实还在，只是搬进了参照实现）；新读法 7.1µs → 4.9µs（比值 0.69，窗口里就那几条覆盖层，剩下的钱在"台上有几格"）。第 1 条的 flake：连跑十次，十次全绿。全量套件 156 passed，**没有改过任何一份已有的测试文件**（`compile.test.ts` 的改动是本轮开始前的自校准，不是为了让它变绿）。

**抓到的第一个坏：道具的第一版时间不递增。** 计划里第 3 条写的是"`propsByFirstT` 前缀一次二分跳过还没上台的"——写出来是错的。`link` 先把名字放进道具表，`paint` 才让它在很久之后落下，于是"第一版落下的时刻"这个数组会回头。修法不是把顺序打乱重排（上画顺序就是层叠顺序，那是语义），而是把可二分的那个数组单独造出来：`reach[i] = min(at[i..])`，右行的前缀最小值。一堂从不"先提名后落笔"的课里 `reach === at`，所以界对常见的形状是紧的，只随那几个晚落的格子松一点。`frame.test.ts` 的不变量那一条把它钉住了：`reach` 不许回头，且它的下标必须和 `props` 一一对应。

**抓到的第二个坏：`visibleName` 和 `visibleProps` 对 `discard` 的说法本来就不一致。** 前者问"这个名字现在看得见吗"时不看 `discardedAt`，后者数台上格子的时候看。对账测试第一次跑就红了这一点（我一开始把参照实现写成"正确答案"，于是红的就是我）。这一卷的规矩是不改语义，所以修的是参照：`frame.test.ts` 里那份 `visibleName` 期望值原样复刻旧的（不看 `discardedAt` 的）读法，并在注释里点名这就是那个不一致。**它是下一件**：一个被 `discard` 掉的名字，镜头"看得见"它，但板上没有那一格 —— 这不是本轮的功课，本轮把它量出来了。

**顺带量到的第三件事（不在计划里，属于诚实性问题）**：`agentSnapshot()` 的道具那一行原本把"这一屏只列 40 格"折掉的格子也算进"在镜头框外"那一类。数没错，话是错的 —— 那些格子就在眼前，只是这一屏写不下，而导演听见"在镜头框外"就会去 pan，pan 完还是看不见。现在三类各有名字：被换场扫走（`recall`）、在框外（`pan`/`fit`）、在框内但这一屏只列这么多（`fetch_prop` 一格一格读）。

**没有做的事，理由仍然成立**：没给整卷条数封顶，没动一个时序常量，没引依赖，`link` 还没被画到板上。第 5 条 brainstorm 里那条现在多了一个同伴：`discard` 与可见性的那一句也得对齐。这两件都是"加/改词汇"，不是"把已有的词汇兑现"，所以它们进下一卷，不混进这一卷的对账 —— 对账测试的价值恰恰在于它比的是**同一份语义**，语义一动，那一千多次逐帧比对就不再是证据。
